# 자동 보고서 작성 기능 — 설계

작성일: 2026-10-20
대상 과제: AX 해커톤 「AI 아차사고 즉석 보고 Assistant (모바일)」 / 안전 트랙

---

## 1. 의도와 배경

지금 NearMiss 앱은 과제정의서가 요구하는 흐름 중 **1단계(현장에서 한 줄 입력)만** 구현되어 있다. 작업자가 음성이나 키보드로 한 줄을 남기면 `{ content, createdAt }` 레코드가 브라우저 localStorage에 쌓이고, 통계 탭이 키워드로 사고 유형을 추정해 차트를 그린다.

빠진 것은 과제의 핵심인 **AI 처리와 정식 보고서 산출**이다. 정의서가 말하는 문제는 "현장에서 사무실로 돌아가 15~20분간 양식을 채우는 번거로움 때문에 아차사고가 구두 공유로만 끝나고 사라진다"는 것이고, 목표는 "한 줄 입력 1분 이내 → AI가 즉시 정식 보고서 초안 생성 → 확인 후 한 번의 터치로 제출"이다. 즉 **양식을 채우는 노동을 사람에게서 AI로 옮기는 것**이 이 기능의 전부다.

여기에 두 번째 문제가 붙어 있다. 위험도(경미/중대) 판단이 작성자 개인의 주관에 의존해서 같은 상황도 담당자마다 다르게 분류되고, 그 결과 통계 신뢰도가 떨어지며 우선순위 높은 사안이 뒤늦게 발견된다. 그래서 **위험도를 AI가 일관된 기준으로 1차 분류**하고, 높게 분류된 건을 관리자가 즉시 볼 수 있게 한다.

### 왜 지금 이 설계인가

정의서에는 보고서 양식이 두 번, 서로 다르게 나온다. 5장 '접근 방향'의 출력은 **경위·위험도·원인 추정·권장 조치** 4항목이고, 6장 '보고서 형식 예시'는 광양 #1 전기로 속보로 **일시·장소·인적사항·발생개요·발생원인(3분류)·재발방지 대책**이다.

브레인스토밍에서 세 안(간결형 / 속보 양식형 / 하이브리드)을 목업으로 비교한 결과 **속보 양식형(6장 양식)으로 확정**했다. 관리자가 그대로 결재·배포할 수 있는 문서가 나오는 것이 이 과제의 가치라는 판단이다. 5장의 4항목은 버리지 않고 속보 양식 안에 흡수한다(아래 3.2).

## 2. 목표

### 정량 목표 (정의서 3장에서 가져옴)

| 구분 | 현재 | 목표 |
|---|---|---|
| 기록 소요시간 | 사무실 복귀 후 PC 양식 작성, 15~20분 | 현장에서 한 줄 입력, 1분 이내 |
| 보고서 작성 | 담당자가 수기로 정식 양식 재작성 | AI가 입력 즉시 정식 보고서 초안 생성 |
| 위험도 분류 | 담당자 주관, 기준 상이 | AI가 일관된 기준으로 자동 분류 |
| 통계·경향 | 담당자가 개별 보고서 취합, 수작업 | 자동 누적 통계로 즉시 확인 |

### 비목표 (Non-goals)

- **사내 SSO·권한 테이블 연동.** 관리자 구분은 환경변수 토큰 하나로 가드한다. 교체 지점에 주석을 남긴다.
- **결재 워크플로.** 상신·승인·반려 단계는 만들지 않는다. 속보 문서를 산출하는 데까지가 범위다.
- **푸시 알림 인프라.** 실제 FCM/APNs·사내 메신저 연동은 하지 않는다(3.6 참조).
- **발생 상황도.** 정의서 6장 예시에 있는 도면·화살표가 들어간 상황도는 생성하지 않는다. 사진 첨부로 대체한다.
- **다국어.** 한국어만.

### 안티목표 (이렇게 되면 기술적으로 동작해도 실패)

- **입력이 다시 양식이 되는 것.** 초안 화면에 필수 입력 칸이 늘어나 작업자가 또 칸을 채우게 되면 정의서가 지적한 원래 문제로 돌아간다. AI가 못 채운 칸이 있어도 **제출을 막지 않는다.**
- **AI가 멈추면 신고가 멈추는 것.** API 장애·오프라인·타임아웃에 신고 자체가 유실되면 "기록 누락 최소화" 목표와 정면으로 충돌한다. 원문은 어떤 경우에도 먼저 저장된다.
- **실명이 외부로 나가는 것.** 개인정보가 LLM 프롬프트나 공유용 문서에 평문으로 드러나면 현장 도입이 불가능해진다.
- **AI 추정이 사실로 보이는 것.** 원인 추정·권장 조치는 AI의 가설이다. 사람이 쓴 사실과 시각적으로 구분되지 않으면 안전 문서로서 위험하다.

## 3. 만드는 것

### 3.1 전체 흐름

```
[신고 탭]  한 줄 입력(음성/키보드)
    │  제출
    ▼
서버에 원문 저장 (status: draft)  ← 이 시점에 유실 위험 없음
    │  POST /api/reports/{id}/draft  → 즉시 202 + job 상태
    ▼
[속보 초안 화면]  "분석 중" 상태로 먼저 열림 (일시·인적사항은 이미 채워져 있음)
    │  GET /api/reports/{id}/draft 폴링
    ▼
GPT가 속보 양식 칸을 채움 + 위험도 분류 + 확인 질문 0~2개 생성
    │
    ▼
작업자가 확인/수정, 확인 질문 답변, 사진 첨부
    │  최종 제출 (한 번의 터치)
    ▼
status: submitted → 통계 누적 + 위험도 '상'이면 관리자 미확인 큐에 올림
    │
    ▼
[관리자 탭]  목록·필터·속보 상세·실명 보기·주간/월간 집계
```

핵심은 **원문 저장이 AI 호출보다 먼저**라는 점이다. AI가 실패하면 초안 없이 원문만 남은 `draft` 레코드가 되고, 작업자나 관리자가 재시도할 수 있다(3.8).

### 초안 생성은 비동기로 한다

**사내 API의 응답 지연을 모르는 상태**이고, 속보 양식 전체(발생개요 시각별 서술 + 원인 3분류 + 대책 + 위험도 + 확인 질문)는 출력 토큰이 상당하다. 동기 호출로 만들었다가 데모 직전에 느린 것을 발견하면 급하게 구조를 바꿔야 하므로, **처음부터 비동기로 만든다.**

- `POST /api/reports/{id}/draft` 는 작업을 큐에 넣고 바로 돌아온다.
- 프론트엔드는 초안 화면을 **먼저 열고** 폴링한다. 시각·인적사항처럼 AI가 필요 없는 칸은 이미 채워져 있어서 빈 화면을 보지 않는다.
- AI 칸은 스켈레톤 상태로 두고, 응답이 오면 채운다.
- 폴링 간격·타임아웃·실패 후 재시도 횟수는 빌더가 정한다. SSE로 바꿔도 되지만 폴링이 더 단순하다.

API가 빨라도 이 구조는 그대로 동작한다(폴링 한두 번에 끝난다). 느려도 깨지지 않는 쪽을 택한 것이다.

### 3.2 속보 문서 양식

정의서 6장 양식을 따르고, 5장이 요구한 위험도를 머리에 배지로 올린다.

| 칸 | 채우는 주체 | 비고 |
|---|---|---|
| 제목 | AI | `{장소} 니어미스 속보` 형태 |
| 위험도 | **AI** | 상 / 중 / 하 — 5장 요구사항 |
| 사고 유형 | **AI** | 기존 `classify.js`의 7개 유형 + 기타 |
| 일시 | 시스템 + AI | 입력 시각이 기본값. 문장에 "어제 오후 2시" 같은 표현이 있으면 AI가 보정 |
| 장소 | **AI** | 문장에서 추출. 없으면 확인 질문 대상 |
| 인적사항 | 프로필 + AI | 소속·성명·직무·인원수·재해 정도 (3.4) |
| 발생개요 | **AI** | 정의서 예시처럼 `HH:MM 무슨 일` 시각별 서술. 시각을 모르면 시각 없이 서술 |
| 발생원인 | **AI** | `[물리적/환경적]` `[시스템/프로세스]` `[조직적]` 3분류 |
| 재발방지 대책 | **AI** | 항목별로 `(즉시)` / `(~MM.DD.)` 기한 표기 |
| 사진 | 작업자 | 최대 2장 (정의서 예시가 2장) |

**AI가 채운 칸은 화면에서 눈에 보이게 표시한다.** 안티목표의 네 번째 항목 때문이다. 작업자가 손으로 고친 칸은 표시가 사라진다. 특히 '발생원인'과 '재발방지 대책'은 AI의 추정임을 문서에도 남긴다.

모든 칸은 제출 전에 수정 가능하고, **빈 칸이 있어도 제출된다.**

**작업자가 보는 화면이 곧 이 속보 양식 전체다.** 브레인스토밍에서 비교한 목업 중 작업자가 속보 문서를 그대로 확인하는 안(B안)이 선택되었다. 간결 요약 화면을 따로 두지 않는다 — 화면은 `신고 입력` → `속보 초안 확인` → `제출` 세 단계다. 스크롤이 길어지는 것은 받아들이되, **읽어야 할 것이 위에 오도록** 순서를 잡는다: 확인 질문 → 위험도 → 일시·장소·인적사항 → 발생개요 → 발생원인 → 재발방지 대책 → 사진. 위험도와 확인 질문만 보고 바로 제출 버튼을 누를 수 있어야 한다(제출 버튼은 화면 하단 고정).

### 3.3 위험도 기준

주관 편차를 없애는 것이 목적이므로 기준을 프롬프트에 명시한다. 아래가 1차안이고, 해커톤 기간 중 현장 담당자 인터뷰로 보정한다(정의서 3장도 시간 목표에 같은 전제를 달아두었다).

- **상** — 그 상황이 조금만 달랐으면 사망·중상으로 이어질 수 있었던 건. 중량물 낙하·전도, 추락, 감전, 폭발·화재, 밀폐공간, 중장비 협착.
- **중** — 부상 가능성은 분명하지만 사망·중상까지 이어지기 어려운 건. 미끄러짐, 경량물 낙하, 베임, 화학물질 소량 접촉.
- **하** — 즉각적 부상 위험은 낮으나 방치하면 위험이 커지는 상태. 정리정돈 불량, 표지 훼손, 통로 적치.

판단이 갈리는 경우는 **높은 쪽으로** 분류한다(안전 보수성). AI는 분류와 함께 **한 줄 근거**를 반환하고, 그 근거를 초안 화면과 관리자 화면에 함께 보여준다 — 근거가 없으면 작업자가 분류를 고칠 판단을 할 수 없다.

기준 문면은 **코드 한 곳(상수)에 두고** 프롬프트가 거기서 읽어가게 한다. 인터뷰로 보정될 때 고칠 자리가 하나여야 한다. 다만 **이미 저장된 건의 일괄 재분류 경로는 만들지 않는다** — 기준이 바뀌면 시드를 다시 깔면 된다. *(설계자 판단)*

분류 정확도를 측정할 라벨링 샘플은 없다. 따라서 **테스트는 파싱·실패처리·마스킹 수준까지만** 두고 분류 품질 평가 스크립트는 만들지 않는다. 품질은 데모 리허설에서 눈으로 확인한다. *(설계자 판단)*

### 3.4 인적사항과 개인정보

정의서 6장 예시의 인적사항(`두원기업 / 박 ○○ 등 3명 / 축로공`)은 **아차사고를 겪은 당사자**이고, 속보를 작성한 주체(`전기로건설 TF`)와 다르다. 두 개를 분리한다.

- **신고자** — 앱 설정에 소속·성명·직무를 **한 번만** 저장한다(localStorage). 이후 매 신고마다 입력 0회. "1분 이내" 목표를 지키기 위한 장치다.
- **당사자** — 초안 화면에 `본인` 체크박스를 기본 켜둔다. 켜져 있으면 신고자 프로필이 당사자로 들어간다. 끄면 소속·인원수·직무를 받고 성명은 선택 입력으로 둔다.

**마스킹은 저장이 아니라 출력 단계에서 한다.** 실명을 안 받으면 관리자가 후속 조치를 못 하고, 마스킹해서 저장하면 복구가 안 된다.

```
저장 레코드    : { name: "박민수", org: "두원기업", role: "축로공", count: 3 }
속보 문서 출력 : 성명 : 박 ○○ 등 3명
```

마스킹 규칙은 정의서 예시를 따라 **성만 남기고 나머지 글자를 `○`** 로, 복수면 `등 N명`을 붙인다. 외자 성과 복성(남궁·황보 등)에 대한 처리, 2글자 이름 처리는 빌더가 정한다.

실명 조회는 **별도 엔드포인트(`GET /api/reports/{id}/identity`)로만** 내려주고 관리자 토큰으로 가드한다. 속보 뷰의 `실명 보기` 토글이 이 엔드포인트를 호출한다. 목록·상세 등 다른 모든 응답에는 마스킹된 값만 담긴다.

**GPT 프롬프트에는 실명을 보내지 않는다.** 초안 생성에 실명이 필요한 이유가 없다. 서버가 요청을 만들 때 인적사항을 `[당사자]` 같은 자리표시자로 치환하고, 응답을 받은 뒤 실명을 다시 끼워 넣는다. 사내 API라도 PII는 최소로 보낸다.

원문(`content`) 자체에 작업자가 이름을 말해버린 경우까지 치환할지는 빌더 판단에 맡긴다. 원문은 분석의 근거이므로 과도한 치환이 품질을 해칠 수 있다.

### 3.5 확인 질문

정의서 5장의 "부족한 정보가 있으면 짧은 확인 질문 한두 개로 보완한다"를 구현한다.

- AI가 **최대 2개**까지 생성한다. 0개도 정상이다.
- 초안 화면 **맨 위**에 띄운다. 답을 넣으면 해당 칸이 다시 채워진다.
- **모든 질문에 `건너뛰기`가 있고, 답하지 않아도 제출된다.** 안티목표 첫 번째 항목 때문이다.
- 질문은 장소·설비처럼 **양식의 빈 칸을 메우는 것**에 한정한다. "더 자세히 말씀해주세요" 같은 열린 질문은 금지다.
- 답변 반영은 초안을 **다시 생성**하는 방식으로 한다(원문 + 질문·답변을 함께 넣어 재호출). 부분 패치보다 단순하고, 답변이 위험도 분류까지 바꿀 수 있다.

**작업자가 이미 손으로 고친 칸은 재생성 결과로 덮지 않는다.** 칸별로 출처(`ai` / `user`)를 들고, `user`인 칸은 잠근 뒤 재생성 결과에서 제외한다. 고친 내용이 날아가면 같은 입력을 두 번 하게 되어 안티목표 첫 번째 항목을 정면으로 깬다. 재호출 프롬프트에는 **사용자가 고친 값을 확정 사실로 넣어** 다른 칸이 그것과 어긋나지 않게 한다. *(설계자 판단)*

### 3.6 알림과 공유

정의서 5장은 "위험도가 높게 분류된 건은 관리자에게 즉시 알림"을 요구하지만, 해커톤에서 사내 메신저·푸시 인프라를 붙일 수는 없다. 대신:

- 위험도 `상`인 건은 `acknowledged: false`로 **관리자 미확인 큐**에 올라간다.
- 관리자 화면 상단에 **미확인 고위험 건수 배너**가 뜨고, 관리자가 열어보면 확인 처리된다.
- 서버에 **웹훅 훅 포인트**를 하나 둔다. 환경변수로 URL이 주어지면 위험도 `상` 제출 시 POST한다. 안 주어지면 로그만 남긴다. 실제 사내 메신저를 붙이는 자리임을 주석으로 명시한다.

### 3.7 오프라인 대응

정의서 5장의 오프라인 요구사항이다.

- 제출 시 서버 저장이 실패하면 **localStorage 큐**에 넣고 "전송 대기 중"으로 표시한다.
- `online` 이벤트와 앱 재진입 시 큐를 비운다(순서대로 재전송, 성공분 제거).
- 오프라인 상태에서 초안 화면은 **AI 없이** 열린다. 일시·인적사항은 로컬에서 채워지고, AI 칸은 "연결되면 자동 분석됩니다"로 표시된다.
- 재전송 시 서버가 원문 저장 후 초안 생성까지 이어서 수행한다.
- 재전송은 **멱등**이어야 한다. 클라이언트가 큐 항목마다 UUID를 만들어 보내고 서버가 중복을 거른다 — 재전송 중 응답을 못 받으면 같은 신고가 두 번 들어간다.

**오프라인 큐에 사진은 넣지 않는다.** 휴대폰 사진 2장을 base64로 localStorage에 넣으면 할당량(약 5MB)을 바로 넘긴다. 오프라인에서는 원문만 큐에 담고, 사진 첨부는 온라인 초안 화면에서만 제공한다. IndexedDB + Blob으로 넓히는 것은 범위 밖이다. *(설계자 판단)*

### 3.8 AI 실패 건(`draft`)의 처리

- **작업자 경로** — "내 신고 내역"에 `분석 실패 · 다시 시도` 상태로 남고, 눌러서 초안 생성을 재시도한다.
- **관리자 경로** — 관리자 목록에 `draft` 건도 **보인다.** 위험도 자리에 `미분류` 배지가 뜨고, 관리자가 재시도하거나 칸을 수기로 채워 제출할 수 있다.
- **백그라운드 워커·스케줄러는 만들지 않는다.** 재시도는 사람이 누를 때만 일어난다.

목록에서 `draft`를 숨기면 막힌 신고가 사실상 사라져서 "AI가 멈추면 신고가 멈추는 것" 안티목표를 위반한다. 그래서 목록·필터에 **상태 축(전체 / 제출됨 / 미분류)**을 하나 더 둔다. 통계 집계에는 `submitted`만 들어간다. *(설계자 판단)*

### 3.9 관리자 화면

신고 화면과 같은 앱의 **세 번째 탭**으로 붙인다. 별도 앱을 만들지 않는다 — 해커톤 데모에서 화면 전환이 끊기지 않는 편이 낫다.

- **미확인 고위험 배너** — 3.6
- **목록** — 최신순. 각 행에 위험도 배지·유형·일시·장소·원문 앞부분. 위험도와 기간으로 필터.
- **속보 상세** — 3.2의 속보 문서 전체. `실명 보기` 토글(3.4). 인쇄/PDF 저장이 되도록 인쇄용 CSS를 넣는다 — 결재·배포용 문서이므로 종이로 나가는 경로가 필요하다.
- **주간·월간 집계** — 정의서 5장의 "주간·월간 리포트로 자동 집계". 기존 통계 탭의 차트 로직(`js/stats.js`)을 재사용하고, 기간 토글(주/월)과 위험도 분포를 추가한다.

관리자 탭 진입에 토큰을 요구한다. 토큰은 설정 화면에서 한 번 입력해 보관한다.

### 3.10 데이터 저장

관리자 화면이 생기면 **다른 사람이 신고한 건을 봐야 하므로** localStorage만으로는 성립하지 않는다. 서버 저장으로 옮긴다.

기존 `js/store.js`는 이 교체를 이미 염두에 두고 `submit()`/`fetchAll()`만 바꾸면 되도록 분리돼 있고 `isLocalOnly` 플래그도 있다. 그 설계를 그대로 활용한다 — `isLocalOnly`는 `false`가 되고, 통계 탭의 "이 기기 기준" 안내가 사라진다.

저장소는 **SQLite 한 파일**로 한다. 서버 코드와 함께 레포에 두되 DB 파일은 `.gitignore`에 넣는다. 스키마는 빌더가 정하고, 최소한 원문·초안 JSON·위험도·상태·확인여부·사진을 담아야 한다.

**데모용 시드 데이터가 필요하다.** 통계와 관리자 목록이 비어 있으면 보여줄 게 없다. 과제정의서 6장의 광양 사례를 포함해 20~30건 정도를 넣는 스크립트를 만든다. 시드는 AI를 호출하지 않고 미리 만들어둔 초안을 넣는다(데모 전에 API 비용·시간을 쓰지 않기 위해).

### 3.11 토큰 없는 사용자에게 내려가는 데이터

`isLocalOnly`가 `false`가 되면 통계 탭은 **남이 신고한 건까지** 집계한다. 그런데 원문에는 작업자가 말로 흘린 이름·소속이 들어 있을 수 있다. 그래서 **원문은 관리자 토큰 없이 내려가지 않는다.** *(설계자 판단)*

| 엔드포인트 | 토큰 | 내용 |
|---|---|---|
| `GET /api/stats` | 불필요 | **집계 수치만.** 일별·유형별·시간대별·위험도별 건수. 원문·장소·인적사항 없음 |
| `GET /api/reports/mine` | 불필요 (신고자 ID로 필터) | 그 기기가 보낸 건만, 원문 포함 |
| `GET /api/reports` | **필요** | 관리자 목록. 마스킹된 인적사항 포함 |
| `GET /api/reports/{id}` | **필요** | 속보 상세. 마스킹된 인적사항 |
| `GET /api/reports/{id}/identity` | **필요** | 실명 (3.4) |

이 구조 때문에 기존 `js/stats.js`는 **레코드 배열 대신 집계 결과를 받도록** 고쳐야 한다. 지금은 `reports` 배열을 받아 클라이언트에서 집계하는데, 그 경로를 유지하면 토큰 없는 아무에게나 전원의 원문이 내려간다. 집계를 서버로 옮기고, `js/stats.js`는 받은 수치를 그리는 역할만 한다.

**"내 신고 내역" 식별** — 클라이언트가 첫 실행 때 UUID(`reporterId`)를 만들어 localStorage에 보관하고 모든 신고에 붙인다. 인증이 아니라 **기기 식별자**다. 신고자 프로필(3.4)과 같은 자리에 둔다. 내역은 서버에서 이 ID로 조회하되, 오프라인에서도 보이도록 로컬 캐시를 함께 유지한다.

## 4. 만드는 방식

브레인스토밍에서 정해진 것들이다.

- **백엔드: Python.** FastAPI. 정적 파일 서빙 + API를 한 프로세스에서 한다. 터미널에서 서버 하나 띄우는 건 괜찮다고 확인했다.
- **데모는 노트북 브라우저의 모바일 뷰로 한다.** `http://localhost:8000` 으로 접속하므로 보안 컨텍스트가 충족되어 **음성 입력과 카메라가 그대로 동작한다.** TLS·터널 작업은 범위 밖이다.
  - 주의: 실기기에서 `http://192.168.x.x:8000` 으로 열면 Web Speech API와 카메라가 차단된다. 나중에 실기기 데모가 필요해지면 자체 서명 인증서나 터널이 별도 과제로 들어간다. 코드에 가정이 박히지 않게, 호스트·포트를 하드코딩하지 않고 상대 경로로만 API를 부른다.
- **LLM: 사내 GPT API.** OpenAI 호환(`/v1/chat/completions`), 인증은 `Authorization: Bearer`. **base URL·모델명·API 키 모두 환경변수**로 받는다. 코드에 하드코딩하지 않는다.
  - 브라우저에서 직접 호출하지 않는 이유: 키가 노출되고, 사내 API가 CORS를 허용할 가능성이 낮다.
  - 구조화된 출력이 필요하다(속보 양식 칸들 + 위험도 + 확인 질문). JSON 응답을 강제하고, 파싱 실패 시 1회 재시도 후 실패 처리한다.
  - 사내 API의 지원 기능(JSON mode, function calling 등)이 불확실하므로 **가장 보수적인 방법**을 쓴다: 프롬프트로 JSON을 지시하고 응답을 파싱한다.
  - **목(mock) 프로바이더 모드를 1급으로 둔다.** `NEARMISS_LLM_MODE=mock` 이면 고정 픽스처를 돌려준다. 테스트에 필요하고, 사내망 밖에서 UI를 만들 때도, 데모 중 API가 죽었을 때 비상용으로도 쓴다. 실제 프로바이더와 같은 인터페이스를 구현한다. *(설계자 판단)*
  - 확인 질문 답변 시 전체 재생성(3.5)이므로 한 건당 호출이 1~3회다. 데모에서 동시 사용자가 붙으면 한도에 걸릴 수 있으니, 호출 실패를 정상 경로로 다룬다(3.8).
- **프론트엔드: 기존 방식 유지.** 빌드 도구·프레임워크 없이 `js/` 아래 전역 IIFE 모듈을 추가하고, `css/style.css`의 기존 토큰과 모바일 우선 스타일을 따른다. 차트도 기존처럼 라이브러리 없이 HTML/CSS로 그린다.
- **접근성.** 기존 코드가 `role`·`aria-*`·키보드 포커스·"표로 보기" 같은 색에 의존하지 않는 경로를 챙기고 있다. 새 화면도 같은 수준을 지킨다. 위험도를 **색만으로** 구분하지 않는다(상/중/하 글자를 함께).
- **테스트.** 서버 쪽 로직(마스킹, 위험도 파싱, JSON 파싱 실패 처리, 오프라인 재전송 멱등성)은 테스트를 둔다. LLM 호출은 목으로 대체한다.

### 환경변수

```
NEARMISS_API_BASE_URL   # 사내 GPT API base URL
NEARMISS_API_KEY        # Bearer 토큰
NEARMISS_MODEL          # 모델명
NEARMISS_ADMIN_TOKEN    # 관리자 탭 가드
NEARMISS_WEBHOOK_URL    # (선택) 고위험 건 알림
NEARMISS_LLM_MODE       # (선택) mock — 고정 픽스처로 응답
```

`.env.example`을 레포에 두고 실제 `.env`는 `.gitignore`에 넣는다.

## 5. 빌더에게 맡기는 것

- SQLite 스키마 설계와 마이그레이션 방식
- API 엔드포인트의 정확한 모양(이 문서가 명시한 `/api/reports/{id}/identity`의 가드 성격만 지킬 것)
- 프롬프트 문면 — 3.3의 위험도 기준과 3.2의 양식 칸을 모두 반영하고, 출력이 JSON으로 안정적으로 나오게 하는 것이 요구사항이다
- 마스킹 구현의 세부(외자 성·복성·2글자 이름)
- 사진 저장 방식(파일시스템 vs DB blob)과 용량 제한
- 초안 화면의 칸별 편집 UI 형태
- 집계 API(`GET /api/stats`)의 응답 모양과, 그에 맞춘 `js/stats.js` 수정 범위
- 폴링 간격·타임아웃·재시도 횟수 (3.1)
- 목 프로바이더 픽스처의 내용
- 시드 데이터의 구체적 내용
- 파일 분할 — 다만 기존 레포의 모듈 하나당 역할 하나 관례는 지킬 것
